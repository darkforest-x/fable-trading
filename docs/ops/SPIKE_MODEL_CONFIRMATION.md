## 页面与通知

前端默认显示指标启动，支持15m / 1H / 4H；另可切换模型确认、等待确认及全部已登记候选，仍支持周期筛选、深浅主题及图表放大。
原始蓄势观察保持独立，不等于信号。确认详情有原箭头、模型核心区间紫框及确认竖线。
紫框纵向是模型核心时间内K线高低包络，非重绘原YOLO纵向边界，也不是止盈止损。
检测分数不是胜率。图表保留原箭头和确认两个时点，不把后来走势当作当时模型输入。

Bark 接受以下事件，前端仅显示 Bark 回执。

|周期|原指标收盘启动|YOLO 同方向确认|
|---|---|---|
|15m / 1H / 4H|直接推送“指标启动 · 未经 YOLO 确认”|另发“YOLO 确认 · 等待 N 根”|

同根通过也保留两种独立消息。模型证明、权重、参数、p..p+9窗口与30分钟新鲜度均不变。
直接通知使用独立启用政策 `imacd-direct-start-notifications-v1`，原事件协议仍为 `imacd-tv-visible-start-monitor-v3`。
新政策首次启用前（含恰好启用时刻）的箭头不补推；旧 raw 政策启用时间不能授权新通知。
15m 使用自己的首次直接通知周期启用时间；1H/4H 与 Bark 通道已有启用时间保留，不因扩周期重置。
只有首次插入原事件时才能创建该阶段 outbox；已有记录不能因切换、补齐行情或重启重新入队。
初始化模型与直接通知政策使用加法，不互相退休对方 pending 消息。重启不重发历史或未知回执。
同一渠道中，原箭头仍在发送或等待限流重试时，模型确认让其先发送；原箭头已失败、未知、跳过或等待到过期则不阻挡新的确认。
发送失败不等于信号失败，未知回执不自动重试。Bark 的 sent 仅证明服务接受，不证明手机展示。
同一原箭头的确认与 Bark outbox 在一个SQLite事务内提交；不同原箭头即使同时确认也各有身份。
Telegram sender 与 model gate 的 Telegram 支路默认关闭，监控不启动 TG 线程、不读取 TG 凭据、不生成 TG 配图或新待发送项；启动测试入口也关闭。
启动时旧 TG pending 标记 skipped/telegram_disabled_by_owner，sent、failed、unknown 等历史回执保留。Bark 队列不受影响。
旧 Telegram 凭据不删除或修改；历史发送机制仅保留用于兼容和显式假发送测试，当前监控没有重新开启入口。
原始OHLC仍只保存在内存；模型队列单线程，按合约×周期合并等待输入，不阻塞公开行情扫描。

## 延迟预算（不变更原30分钟数值）

|阶段|15m|1H|4H|
|---|---:|---:|---:|
|箭头至最晚可确认的K线|9×15m=135分钟|9小时|36小时|
|公开扫描轮询间隔|120秒|120秒|120秒|
|全市场扫描、模型队列耗时|实时读scan.duration_seconds及model_gate.queue_depth；无固定保证|同左|同左|
|单端点2图首次MPS实测|约1.9秒，仅单实例冒烟，不代表全市场峰值|同左|同左|
|确认收盘至允许推送|≤30分钟|≤30分钟|≤30分钟|

第一行是允许等待模型的结构窗口，不是“原箭头仍新鲜”。模型通知入队、Bark发送前复核、前端新鲜徽章均使用确认收盘+30分钟。
15m/1H/4H 直接阶段都没有模型等待，但仍须箭头收盘，再经历扫描和通知服务耗时；三个环节使用原箭头收盘+30分钟。
两个阶段的日期/价格分别展示，不把模型确认改写成更早的指标入场价。模型异常不阻断任何周期的直接阶段；健康页仍会如实报告模型异常。
超过新鲜度的真实确认可以保留为历史，但不能把检测完成的墙钟时间当成信号发生时间。
新登记候选须仍有可能落在9根等待+30分钟内；不为7天旧箭头补跑大批模型。
本机通知流独立，不更改VPS执行器原有30分钟门或15分钟脉冲。
