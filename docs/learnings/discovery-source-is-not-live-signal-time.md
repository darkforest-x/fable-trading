# 服务发现的记录不一定是实时信号

- **问题**：V1 启动扫描回算出的 158 条旧箭头与首次启用后 1 条新箭头都保存为 `source=live`，导致信号中心把预热历史混入实时列表。
- **死胡同**：仅按 `source` 分类会混淆发现渠道与事件发生时间；只在浏览器过滤第一页会产生缺页和错误游标；改成 `source=replay` 又会冒充有冻结回测证据的正式回放。后续清理时间和当前通知开关也不能代表首次启用时间。
- **有效路径**：读取幂等保存的 V1 首次 arm 回执，用原始箭头收盘时间在 SQL 的 LIMIT/游标之前划分实时与预热。YOLO 使用其原始箭头时间，避免延后确认把旧启动变成实时。独立 `display_scope` 保留事件 source、证据和通知回执。缺失可信边界时明确返回未就绪，不猜当前时间。
- **通用规则**：区分采集渠道、事件时间、发现时间与展示分类。历史分栏应是只读视图，不应重写事件来源或重新触发通知。
- **牵连**：`yoyo/monitor/server.py`、`store.py`、`static/`；`notification_policy:v1_bark_arm` 是本次分类的固定依据。未改变策略、Bark/TG 通知条件或原始记录。
