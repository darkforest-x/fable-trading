# Reload an unresponsive macOS permission panel before changing the bridge

- **Problem**: On 2026-09-08, the owner could not enable `caffeinate → System Events` in macOS Automation. This was a nonresponsive switch, not a successful grant followed by a failed TradingView navigation. Both AX and screenshot observations still showed `off` after clicking, with no authentication dialog.
- **Dead ends**: Clicking by accessibility element and by observed coordinates, clearing the settings search, and navigating back into Automation did not persist a change. Monitor health was good; modifying the scanner or restarting its LaunchAgent would not explain this UI failure. Broad TCC logs contained unrelated denials and did not establish a specific underlying OS defect.
- **Effective path**: Quit only System Settings with Command-Q, reopen it, and navigate through Privacy & Security → Automation. Expanding caffeinate and clicking the switch then produced the normal Touch ID / password dialog. Authentication must be completed by the owner in the system UI. At this observation the dialog was reached, not proof that permission had been granted or that the live chart bridge had passed.
- **General rule**: Distinguish click acceptance, authentication, persisted permission state, and the actual service-context operation. Reopen a stuck settings UI before changing process identity, resetting privacy databases, or modifying a previously working bridge. An observed recovery after reload is evidence of the workaround, not a diagnosis of the OS's internal cause.
- **Scope**: `yoyo/monitor/tradingview.py`, `tradingview.applescript`, and the caffeinate-wrapped LaunchAgent are relevant context only; no runtime code, signal rules, model configuration, credentials, or privacy database was changed during this diagnosis. Related lesson: [Verify navigation from service context](desktop-navigation-must-be-verified-from-service-context.md).
