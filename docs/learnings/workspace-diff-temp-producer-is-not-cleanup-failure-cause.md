# 确认临时文件的生成者，不等于确认清理失败的原因

- **问题**：2026-09-14 磁盘仅剩约 127 MB，用户临时目录中大量 `tmp.*` 文件累计约 35.1 GB，内容是仓库相对路径清单。同轮清理后临时文件继续增长。
- **死胡同**：只依赖旧清理记录、Docker.raw 的表观大小，或把“文件留下来了”直接归因于强制终止。前者不能解释新增占用，后者缺少信号或退出状态证据。直接递归清空临时目录还会误删正在使用的文件和其他应用数据。
- **有效路径**：捕获到 Codex 子进程执行的 `codex-workspace-diff unstaged false false false 1500 9000` 脚本。其中 `make_temp_file` 创建路径文件，`run_git_capture ... git ls-files --others --exclude-standard -z` 写入未跟踪文件清单；脚本也注册了正常退出清理用的 `trap cleanup EXIT`。结合完整内容格式校验、SHA-256、稳定的文件身份和无打开句柄，清理了 398 个过期清单，分配块合计约 28.3 GB。源脚本捕获记录在本机 `~/.local/state/disk-cleanup/20260914/observed-codex-temp-generator.txt`。
- **通用规则**：区分三个命题：谁写了文件、为什么文件变大、为什么文件没被清掉。生成命令和仓库中的大量未跟踪产物可解释前两者；第三者仍需退出、信号或错误证据。本次没有修改应用、Git 排除规则或启动定时清理，清理失败原因尚未证实，不能声称已经根治。
- **牵连**：保留新生成及内容不匹配的临时文件，保留活跃研究数据。当前目录占用与本轮净释放空间还受到后台写入、共享块和 APFS 空间管理影响，以清理前后 `df` 实测为准，不能把各目录体积直接相加当作净释放量。见 [目录体积不等于可回收空间](apfs-directory-size-is-not-reclaimable-space.md)。
