# 账户能连接、执行器在运行、订单已成交是三种不同事实

- **问题**：把 OKX 实盘状态放进已有信号中心。页面已有参考收益，另有免登录公网入口；简单复用“已连接”状态会让用户误以为在交易，简单复用历史开单会把模拟结果变成实盘收益。
- **死胡同**：实现前排除了三个捷径：用 API 鉴权成功表示运行中；用已有参考 R 填实盘收益；只检查 loopback Host/Origin 就暴露账户接口。前两者缺少执行或成交证据，第三种会漏过主动把 Host/Origin 重写为 loopback 的公网网关。锁文件存在或旧心跳也不能证明进程仍存活。
- **有效路径**：账户读取、进程锁与心跳、本地逐信号执行回执分别投影；只读 SQLite 不构造会初始化数据库的 Store。API 返回白名单字段，交换机请求仅 GET，按需独立线程缓存。失败保留带时间的旧快照，首次失败显示未知；成功空仓才显示 0。凭据变化清掉旧账户快照，避免慢请求把旧账户重新写回缓存。公网网关标记优先于重写后的来源头。
- **通用规则**：先为界面每个状态与数字写明其证据来源和时钟，再做布局。连接状态不能替代执行状态；计划风险、参考收益与真实成交结果必须分开。跨越访问边界时，检查真实代理行为而非假设 Host 代表来路。
- **牵连**：`yoyo/okx_execution/dashboard.py`、信号中心 `okx-execution.js/css`、`public_tunnel.py` 的 `X-Fable-Gateway` 标记。账户权限和订单字段依据 [OKX V5 官方文档](https://www.okx.com/docs-v5/en/)。无账户写接口、不接入信号脉冲、不改交易规则。本轮真实查询观察到账户由先前单向变为双向，只记录最新事实，不归因于本次只读代码。
