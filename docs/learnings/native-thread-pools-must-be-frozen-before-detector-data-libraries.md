# Native thread pools must be frozen before detector data libraries

- **Problem**: P1's first real detector dry-run died with native `SIGSEGV (139)` and no Python exception. Reducing the explicit render pool to one did not help. The same image and weight succeeded only when OpenCV and torch thread counts were fixed before pandas/numpy initialized. A second independent crash occurred when Ultralytics 8.4.89 received a one-element list; passing the identical ndarray directly succeeded.
- **Effective path**: Configure `cv2.setNumThreads(0)`, `torch.set_num_threads(1)`, and `torch.set_num_interop_threads(1)` at process import time, before data libraries. Keep explicit Python render parallelism. Normalize a one-image batch to the ndarray source while preserving multi-image lists. Then require two real replays to produce the same dataset SHA and compare a positive detector window through ndarray and lossless PNG transports.
- **General rule**: Native scheduling is part of reproducibility and must be established before libraries create their pools. A process-level crash is not a droppable bad sample. Minimize it by stage (load, render, inference, postprocess), preserve model/threshold bytes, and prove the scheduling-only fix with output parity instead of upgrading dependencies blindly.
