# 状态计数也必须读取精简投影，SQL JSON 并不会避开大字段解析

- **问题**：信号中心已有 `market_summaries`，但后台状态计数仍对完整 `markets.payload` 调用 `json_extract`。2026-10-16 本机只读样本中，完整表页约 269 MB，摘要约 5.6 MB；相同计数查询五次耗时约 5.6–12.8 秒与暖读 8–10 毫秒。
- **死胡同**：仅给列表接口缓存，或认为 SQLite 内置 JSON 查询不在 Python 解码就很便宜，都会漏掉后台扫描大字段的成本；递归 deepcopy 的行缓存实测也会吃掉数据库读取节省，改为 C 实现的精简 JSON 解码并复测。缓存整个响应也会冻结新鲜度和日界线。
- **有效路径**：状态计数读取与完整记录事务一致的摘要；旧数据尚未回填时显式不可用。HTTP 只缓存精简的信号行 JSON，按 SQLite `data_version` 跨连接失效；时间筛选、未来排除和新鲜度仍每请求重算，缓存有容量与时效上限。
- **通用规则**：先区分磁盘页读取、JSON 解析、统计计算与 HTTP 交付，再优化实测最重的层；确认摘要与原查询计数一致，测试跨进程更新和跨时间边界。
- **牵连**：`yoyo/monitor/store.py`、`signal_cache.py`、`server.py`；不清理历史数据库，不改变扫描频率、信号或实盘执行规则。秒级改进属于后台状态计数，不能宣称为页面整体加速倍数。
