# 状态页不能与扫描写入争夺同一条 WAL 读路径

- **问题**：首轮扫描每个单元持续写入 SQLite 元数据时，`/api/status` 的完整读取会在 WAL 共享锁上等待 5–12 秒；同一快照离线读取不足 100ms，说明问题是在线读写争用而非状态计算本身。
- **死胡同**：只将历史 JSON 统计改为 SQL 聚合。聚合减少解码工作，却不能保证 HTTP 处理器取得读锁；把超时归因于监听器或模型进程也无法解释离线与在线的差异。
- **有效路径**：后台单线程低频生成完整状态快照，原子替换最后一次成功值。请求只复制该值，冷启动或刷新失败明确返回 `stale` 与 `snapshot_at_ms`，不会把锁等待变成 HTTP 挂起。首轮 OHLCV 读取可最多并发 8 个，但因果重放、递归缓存和 SQLite 写入仍按原单元顺序执行。
- **通用规则**：读路径若面对持续写入，仪表盘响应必须与实时数据库读取解耦；并发只用于无状态 I/O，状态递推与持久化必须保留确定顺序。
- **牵连**：`yoyo/monitor/service.py`、`yoyo/monitor/v1_worker.py`、`tests/monitor/test_v1_status_snapshot.py`、`tests/monitor/test_v1_worker_cache.py`；不改变 SPIKE V1 条件、通知资格、风险或任何回测收益。
