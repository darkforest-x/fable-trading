# 榜单漏报必须先区分指标事件与实际通知契约

- **问题**：Owner看到当天涨幅榜，认为11币全部没有抓到；线上扫描健康，但这不足以解释此前是否漏报。
- **死胡同**：直接把上涨归因为模型太严、周期太大或服务故障，都会跳过关键身份差异。当前Python同时记录zero_breakout、dense entry和可见focusRelease；只有后者在当前showMarks=false口径下是通知。历史重建的箭头也不能充作当时发出的提醒。
- **有效路径**：固定截图截止时间，以币种×周期×方向×事件种类×收盘时间连接图表和真实队列；再分开核对检测时间、独立周期启用时间、Bark服务接受回执。冻结44个窗口后，从已清空状态独立重放focus计数；10,396根一致。GRASS今日确有两阶段Bark接受，ZEC30m箭头发生在启用前；IOST/MINA/GPS/ENA另有内部密集启动，但不足双线连续近零12根，所以并非当前可见释放事件。
- **通用规则**：先问“用户期待哪类事件、代码产出哪类、推送允许哪类”，再谈参数优化。主线精确零轴根数与max(abs(md),abs(sb))的连续近零根数是不同变量。持续趋势不每天重新启动；赢家榜单只能定位漏检形态，不能证明放宽条件后的净收益。
- **牵连**：`yoyo/monitor/signals.py`、`notification_policy.py`、Pine V2.6的showMarks/focusRelease、只读通知账本；复核器`yoyo/evaluation/spike_gainers_audit.py`。本次仅诊断，无Pine、阈值、模型、服务或通知变更。
