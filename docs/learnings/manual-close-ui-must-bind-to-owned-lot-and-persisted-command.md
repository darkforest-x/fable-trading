# 平仓界面必须绑定分笔和已持久化指令

- **问题**：形态巡检只展示账户持仓，现有逐笔平仓能力仅在另一套页面可用；同币合并仓位不能直接视作一笔可平的订单。
- **死胡同**：仅按币种增加「平仓」并在网络失败时重试，会丢失分笔归属并可能重复确认；直接复用另一页面 URL 也不能证明当前服务实际安装了对应路由。必须追踪当前页面→API→已运行消费者的完整路径。
- **有效路径**：当前持仓先与系统分笔核对数量，再按 lot_id 生成 60 秒预览；本人确认只持久化同一 command_id。原锁定执行器重验账户、数量、保护与有效期，处理本笔保护单及市价退出。浏览器丢失确认回执只 GET 查询，重新打开仍沿用原指令，done 只在成交回执核对后显示。管理服务就绪检查独立于新开仓门。
- **通用规则**：账户聚合行是展示维度，交易授权必须落到明确分笔；确认响应未知不等于失败，也不允许换新身份自动重试。桌面/手机验收使用拦截的模拟交易回执，真实服务只检查读状态与路由。
- **牵连**：`yoyo/okx_execution/manual_api.py`、`manual_commands.py`、`yoyo/monitor/static/manual-account.js`、`manual-close.js`；未变更风险阈值、账户凭据或实盘执行算法。相关 API 与前端测试覆盖确认口令、过期、重复点击、回执丢失、仓位变化和离线成交全链路。2026-10-19 Owner 明确豁免本次平仓 UI 的 Stitch 生成失败，沿用已有组件；形态 K 线预览独立使用成功生成的 Stitch 设计，并按 Owner 最新要求放大至 65%。
