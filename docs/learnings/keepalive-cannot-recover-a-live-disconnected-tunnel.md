# Process KeepAlive cannot recover a live but disconnected tunnel

- **Problem**: The public endpoint returned Cloudflare 1033 again at 2026-10-26 21:23 Beijing (Ray `a509c636add32b4d`), about three hours after a successful manual reconnect. The origin and correctly addressed gateway returned 200. Cloudflare reported no active connection, while the same connector PID and its local `/ready` still claimed two healthy connections. Both TCP sockets remained established through Shadowrocket fake-IP addresses.
- **Dead end**: Repeating a manual restart restores access but leaves the detection gap intact. launchd `KeepAlive` responds to process exit, not end-to-end service failure. Fake-IP routing and fixed HTTP/2 identify the transport path, not proof of which network component caused the disconnect; request cancellation logs alone do not establish that cause. No matching system sleep/wake event was found in the inspected 18:00–21:24 window.
- **Effective path**: Recover only the existing public connector, then add an independent bounded checker. Three consecutive authenticated-by-TLS Cloudflare 530/1033 responses, with healthy origin and gateway, authorize one restart of the exact existing LaunchAgent. Require the Cloudflare response headers and explicit error code; do not infer 1033 from arbitrary network errors. Record attempts before invoking launchctl, keep a 10-minute cooldown and a three-attempt hourly cap, and reset the streak after a missed interval. No market scan workload or trading service restart is involved.
- **General rule**: Use process supervision for crashes and end-to-end checks for silent disconnection. Recover only the component localized by evidence. Validate classification and failure/cooldown paths without taking production offline. A passing short check establishes current recovery, not long-term network reliability.
