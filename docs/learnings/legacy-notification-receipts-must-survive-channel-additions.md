# 给旧通知账本增加渠道时保留原回执语义

- **问题**：周一 1.618 同时供网页和 App 展示，增加 Bark 时仍须维持一份首次触及事实；旧 `touches.status` 已代表 Telegram 的投递结果。
- **死胡同**：设计时排除直接把旧状态改成“任一渠道成功”，这会丢失 Telegram 回执含义；重新遍历历史触及来建 Bark 队列也会把启用新渠道误变成补发授权。
- **有效路径**：保留旧表和默认 Telegram 接口，在同一 SQLite 事务中仅随新触及插入 Bark 队列，复用周、合约、上下侧唯一键。Bark 独立启用时间、代次、认领和回执，独立发送线程；未能证明发生于启用后的当前分钟影线不入队。迁移、并发、回滚、超时与跨渠道开关用假发送器验证。
- **通用规则**：先辨清共享的是市场事件还是投递结果；展示入口可以共用事实，但每个渠道必须有独立授权边界与回执。新增订阅不能反向改写历史证据。参见 [独立投递状态](notification-channels-need-independent-delivery-state.md)。
- **牵连**：`yoyo/monitor/monday_fib.py`、`monday_fib_service.py`、`monday_fib_bark.py`。Bark 使用独立私有目录，不改其他信号的设备配置；90 秒新鲜度、每周每侧首次触及和断线历史核对保持原义。
