# 历史模拟盘必须把时间推进与原生撮合一起持久化

- **问题**：手机回放需要暂停、切换和重试；HTTP 超时并不代表开仓没成交，重新读取行情重建账户也可能改变旧成交。
- **死胡同**：只在手机保存光标会把未来行情混入判断；请求重试重新编号会重复开仓。另一个实际陷阱是按日预取后提前验证未来 OHLC，使未来坏数据拒绝此前合法回放；仅挑最高周期文件还会让短历史遮蔽完整低周期历史。
- **有效路径**：服务端独立 SQLite 账本将原操作编号、版本、实际喂给 Nautilus 的历史 bar、原生命令和成交快照一起提交。失败则丢弃未提交 worker，恢复只重放已提交命令，不重新读取旧行情。价格验证和图表响应均受已提交时钟约束；在相同显式来源内选择能覆盖请求时段的历史周期。
- **通用规则**：先明确谁拥有模拟时钟、哪些请求能被重发、如何证明恢复后的账本相同，再做播放按钮。预取是 IO 优化，不是允许未来数据参与当前判定。
- **牵连**：`yoyo/discipline_app/replay_history.py`、`replay_store.py`、`replay_api.py`，`yoyo/layers/l3_backtest/replay_native.py`；Nautilus 1.231.0 独立环境，1x 本金约束、逐次 maker/taker 费、O-H-L-C 假设。鉴权不调用真实账户 resolver，模拟操作不进入交易所写端点。原生、存储测试及隔离手机浏览器覆盖断线重试、恢复、缺口和双向挂单。
