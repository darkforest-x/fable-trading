# Provider response waits and input freshness need separate budgets

- **问题**：The ZAMA review on 2026-09-24 stopped after 90.08 seconds without an HTTP response. Earlier max-reasoning reviews had succeeded in 87 seconds, and some had already timed out before the longer v4 rules. The adapter applied 90 seconds to every HTTPX timeout phase and gave even HTTP 408 the same elapsed-time claim.
- **死胡同**：Increasing snapshot lifetime, blaming the rules alone, lowering the owner-selected reasoning effort or automatically replaying failed calls would not establish the cause. The old trace did not identify the timeout phase; provider latency versus connection trouble remained unknown. No such workaround was applied.
- **有效路径**：Separate read inactivity (300 seconds), connection (15), write (30) and pool (5) budgets; persist the local timeout phase and distinguish provider HTTP 408. Keep max reasoning, saved inputs and no automatic retries. A loopback-only HTTP response delayed 91 seconds completed once in 91.06 seconds, without a provider call. The vision suite passed 190 Python and 34 Node tests; this verifies the wait path, not future provider availability.
- **通用规则**：Compare failed elapsed time with successful calls, then identify the phase before changing a timeout. HTTPX read timeout limits inactivity while receiving data, not total request wall time ([official semantics](https://www.python-httpx.org/advanced/timeouts/)). Results still describe the image captured at submission; waiting longer cannot refresh its contents.
- **牵连**：`yoyo/vision_research/zhipu.py`, the manual pending hint in `static/app.js`, and provider/exchange tests. The 90-second snapshot admission check, 12-bar recheck window, serialized automatic queue and unknown-call/no-retry policy remain in force. Reload only the local vision service while no recognition calls are running; do not rewrite past failures.
