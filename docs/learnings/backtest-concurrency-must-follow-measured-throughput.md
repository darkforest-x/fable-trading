# Tune backtest concurrency from throughput, not CPU count alone

- **Problem**: Two native Monday studies were running on a shared 10-core, 16 GB Mac. Eight workers competed with browser and monitoring processes; CPU saturation and roughly 6–7 GB of compressed memory coincided with slow completion. The external disk showed little traffic during the sampled interval, so its earlier outage did not explain this slowdown.
- **Dead end**: More workers would add contention without measured throughput evidence. Neither existing process pool supports a safe live worker-count change. A brief, reversible eight/five/eight-worker scheduling probe was inconclusive and all eight workers were restored. Its raw CPU counters were not unit-calibrated and must not be reported as CPU seconds or used to claim a speedup. A remote GPU also is not evidence of compatible native backtest capacity; the owner subsequently required Mac-only execution.
- **Useful approach**: Read completed per-asset receipts, calculate recent 15/30/60-minute completion rates, and inspect process identities, CPU, memory and disk together. Keep successful assets frozen and preserve the original worker pools and dependent validators. At 21:40 on 2026-10-24, the studies had 392/633 and 337/633 successes, zero failure markers, and all eight workers were runnable. Improved recent throughput was observed, but was not attributed to the probe.
- **General rule**: Distinguish native execution cost, resource contention, and downstream analysis. Report an ETA range from recent completed work, explicitly excluding unmeasured postprocessing. Do not promise an acceleration from additional concurrency or a short, confounded sample.
