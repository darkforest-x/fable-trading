# 延迟入场必须保留原候选时钟与绝对止损

- **问题**：把已研究的 SPIKE 回踩策略移植到 V13.0 Pine，必须只改变入场时机；普通/联合候选、止损和退出的含义不能在移植时悄悄变化。
- **死胡同**：直接替换旧脚本内部的持仓参考，会反过来改变联合信号的生成条件；用确认价或次开重新计算止损，则把原本的延迟入场试验变成了另一套风险策略。仅通过语法检查也发现不了这些语义变化。
- **有效路径**：保留 V12.8 候选与联合引擎，在独立状态层按原信号收盘冻结高低价位和绝对止损。三个确认步骤分别使用不同的已收盘 K 线，确认后次开重算 R；进场当根也测试旧保护，收盘生成的新保护下一根生效。用既有 Python 确认函数生成 20 个 Pine 原生断言，再以同一 Pine 生命周期代码覆盖多空、进场即止损、反向次开、缺口截尾和占仓确认过期。
- **通用规则**：移植入场规则前，先列清候选时钟、冻结量、更新量与生效时钟。保留原候选生成依赖，分别核验状态机与执行顺序；工程等价检查不能冒充跨数据源的收益复现。
- **牵连**：`yoyo/evaluation/spike_v130_delivery.py`、`spike_v130_probe.py`、`pine/spike_v130_retest_core.pine`、`pine/spike_v130_retest_layer.pine`；原研究 `exp-spike-v128-retest-entry-20260923-v1`。0.2% 成本、24 根等待、原止损与 2R/4ATR 退出均不改。Pine 次开参考在该根收盘完成路径核验，确认提醒在前一根收盘产生；不是账户成交回执。
