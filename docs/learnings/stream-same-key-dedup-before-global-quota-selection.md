# 同键去重先流式压缩，再做全局配额选择

- **问题**：15m 全市场检索在第一个高频币种就产生 5631 个原始候选；若把所有候选字典
  留到最后再去重，311 个可用源会把近 200 万条对象同时留在内存里，首轮进程因此被中止。

- **死胡同**：因为最终还要跨币按分数排序，就默认所有上游候选也必须先全量物化。
  这混淆了两种关系：224-bar 排斥只发生在同一 `symbol × side` 内，而每币/每日配额与
  全局排名才需要跨组信息。为了后一个全局步骤，没必要保留前一个步骤必然淘汰的对象。

- **有效路径**：每个源完成评分后，先按冻结的分数与时间次序执行**完全相同的同键去重**，
  只把局部幸存者交给全局配额选择；全局排序、每日上限和每币上限均保持不变。
  测试钉住流式实现与原始批处理实现逐项等价。正式扫描从 1,980,928 个原始候选精确压缩到
  43,526 个去重候选，最终在约 13 分钟内选出 1000 个，未改变冻结配置。

- **通用规则**：先画清淘汰关系依赖哪些键。若排斥关系完全局限在同一键内，就在键生命周期
  结束时做精确流式压缩；只有真正依赖跨键比较的幸存者才进入全局内存。优化前后必须用小样本
  等价测试证明集合与次序不漂移，不能用“结果数量一样”代替。

- **牵连**：`yoyo/datasets/fifteen_minute_launch_candidates.py`、
  `scripts/collect_15m_ma_launch_candidates.py`、`tests/test_fifteen_minute_launch_candidates.py`，
  去重窗口为 224 根；`experiments/active/exp-15m-ma-launch-candidate1000-v1/preregistration.json`
  的筛选与配额参数未改变。
