# 清理浏览器旧副本要按活跃引用判断，不能只按日期判断

- **问题**：2026-09-10 owner 明确授权“哪些能删掉的，先删掉”。前一轮只读盘点发现 Chrome 签名临时副本累计约 73.8 GB，但浏览器仍在使用，不能清空整个目录。
- **死胡同**：只保留最新副本并不安全。本机最新副本是 `code_sign_clone.zNFs0v`，实际被进程映射的却是更早的 `JiQBxl` 和 `bP7RVz`。用更新时间替代活跃引用，可能删除仍在运行的程序；先关闭所有应用又会打断工作。
- **有效路径**：先检查所有副本结构和创建时间，再用 `lsof` 识别打开或映射的路径。只将标准 Chrome bundle、超过 24 小时且未见活跃引用的 41 份副本列为候选，删除前重新检查引用，并把路径严格限定在同一个签名临时目录的直接子目录。保留两份活跃副本及一份较新副本。另通过 pip/npm/uv 自带命令清理包缓存；只清理已确认闲置的 Claude/Cursor/Xcode 缓存、Python 字节码和已安装版本的更新暂存包，没有退出应用或删除项目数据。
- **通用规则**：活跃引用优先于“最新”或“最旧”的推断。先做具体白名单，再执行有范围限制的清理；用途不明的临时文件和应用状态数据库不因体积大就进入清单。目录扫描大小与卷级实际回收量分开记录，不能宣称清掉 41 份就释放了它们 `du` 大小之和。
- **牵连**：本轮清理前可用空间 7.452 GB，最终复测 21.818 GB，净增加约 14.366 GB；这是包含包缓存、应用缓存、更新包和 Chrome 副本的整轮卷级变化，期间其他应用仍在写盘，不能精确归因到每个目录。41 份副本及 11 项缓存/暂存目录均已确认不存在。详细执行记录为 `/tmp/codex-disk-cleanup-record-20260910.json`，候选清单为 `/tmp/codex-cleanup-chrome-candidates-20260910.json` 和 `/tmp/codex-cleanup-app-candidates-20260910.json`；临时记录不保证跨重启保留。
