# 评估类依赖不能和训练 venv 共用一个环境

**日期**：2026-08-20（开源框架评估）
**结论**：`pip install cleanlab` 会把 numpy 从 2.0.2 降到 1.26.4，
而主 venv 的 numpy 版本是 **Mac↔3060 训练契约的一部分**。

## 现象

评估几个开源库能不能帮到项目，先用 `pip install --dry-run --report` 看依赖代价：

```
cleanlab → 新增 3 个包：cleanlab 2.7.1, numpy==1.26.4, termcolor 3.1.0
aeon     → 新增 6 个包：aeon 1.1.0, numba, llvmlite, pandas==2.2.3, ...
```

**两个都在降级主 venv 的固定版本。**

## 为什么这在本项目是硬伤

`scripts/train_on_3060.sh` 开训前比对 Mac 与 3060 两端的
`torch | ultralytics | numpy` 版本，不一致直接 `die`，理由写在脚本里：

> 版本不一致 -> 结果无法与历史曲线对照。先对齐再训。

也就是说主 venv 的 numpy 版本不是一个「装什么都行」的实现细节，
**它是一份跨机契约**。在 Mac 上降 numpy 会：

1. 让 `train_on_3060.sh` 从此拒绝开训（直到有人去 3060 上也降一遍）；
2. 更糟的是——如果有人「顺手」把 3060 也降了对上，那么**降级之后跑出来的数字
   与降级之前的历史曲线不再可比**，而这件事不会有任何报错。

第 2 条是真正的危险：版本检查保护的是可比性，而绕过保护的最自然方式
恰恰是「把两边都改成一样」。

## 处置

评估类依赖一律进独立 venv，`requirements-eval.txt` 单独维护并在文件头写明原因：

```bash
python3 -m venv /tmp/fable_eval_venv
/tmp/fable_eval_venv/bin/pip install -r requirements-eval.txt
```

装完**复验主 venv 没被动过**（本次实测：numpy 仍 2.0.2、pandas 仍 2.3.3）。

## 可迁移的判断

- **评估一个库的第一步是 `pip install --dry-run --report -`，不是 `pip install`。**
  它会把依赖解析结果打成 JSON，能一眼看出哪些版本会被动。花 5 秒，省一次环境重建。
- **区分「依赖」和「契约」。** 一个被跨机版本检查覆盖的包版本不是依赖，是契约；
  改它要走改契约的流程，不能当作装包的副作用。
- **版本一致性检查会诱导一种特定的错误修复方式**：报错说两端不一致，
  最省事的修法是把另一端也改掉——而那恰好是最坏的修法。
  这类检查最好在报错信息里写清楚「对齐的正确方向是哪一边」。
- 同族问题：任何「为了试个新东西而动共享环境」的操作，
  代价都不在试的那一刻，而在下一个人发现结果对不上的时候。
