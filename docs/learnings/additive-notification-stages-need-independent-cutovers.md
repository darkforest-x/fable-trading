# 增加通知阶段时，事件身份与发送政策必须分开

- **问题**：Owner 要求 1H/4H 原箭头先提醒，YOLO 通过后追加。旧系统也曾直接发送原箭头，数据库保留旧启用时间和回执。
- **死胡同**：审查时排除了直接恢复旧 raw 政策：它会把旧启用时间当成新授权；现有 activation 还会每次退休“不属于本协议”的 pending，两个阶段在重启时会相互吞队列。只把消息文案分开也无法处理同根确认与首次通知限流造成的顺序倒置。
- **有效路径**：原箭头保持不可变身份，新直接阶段另设政策与渠道/周期 cutover；首次插入事件才入队，重启只加法恢复政策。派生确认仍用自己的身份与时间。每个渠道的确认 claim 等待同一原箭头的 pending/sending，终态或已过期原箭头不阻挡新的确认。真实临时 SQLite + 假 HTTP 检验同根、跨根、限流、未知、重启和历史边界。
- **通用规则**：扩展既有通知路由前，先核对身份、启用边界、去重、依赖顺序四件事。旧事件的存在不代表新政策允许重发，模型确认也不能回填成首次启动。
- **牵连**：`yoyo/monitor/notification_policy.py`、`store.py`、`service.py`、两个渠道 worker、前端分阶段列表。信号/模型参数与30分钟新鲜度保持，15m仍模型确认才通知。
