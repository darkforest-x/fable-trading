# Retiring a paper feature must also retire its persisted campaigns

- **Problem**: Removing the web paper desk's bulk 1.618 button also requires stopping previously enabled recurring orders. The owner separately requested deletion of one practice account containing open simulated positions.
- **Dead end**: Removing only the button or API would leave persistent campaign settings and an ordinary limit-order matcher able to fill old orders. Deleting only an account row would orphan positions, fills and idempotency receipts because the ledger has no cascading foreign keys. Neither shortcut was deployed.
- **Effective approach**: Before ordinary worker startup, atomically disable campaign settings, advance their generation fence and cancel only pending campaign-owned orders. Keep manual orders, positions and history intact. For the explicitly deleted account, first create a private consistent SQLite backup under a reserved write transaction, remove its dependent rows and receipts, and compare all surviving relations with the backup before committing. Do not fabricate closing trades for deleted paper positions.
- **General rule**: Inventory the UI, routes, worker, persisted configuration and fill authorization as separate retirement surfaces. Account deletion additionally needs an exact identity, a recoverable backup, dependent-record coverage and evidence that other accounts are unchanged.
- **Scope**: `yoyo/research_workspace/monday_bulk_retirement.py`, `paper_desk_api.py`, `yoyo/monitor/server.py`, `tests/research_workspace/test_monday_bulk_api.py`. This concerns local simulation only; no exchange order or real-money authority changes.
