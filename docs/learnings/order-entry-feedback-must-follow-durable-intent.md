# 开单反馈要跟随持久化请求，而不是网络返回先后

- **问题**：止损与开仓方向分开选择造成重复操作；提交回执较慢时，即使状态查询已经确认成交，按钮仍可能等待旧请求返回。
- **死胡同**：缩短所有轮询间隔会提前触发“未送达”请求封存；简单取消等待或在超时后重发又可能重复下单。受理、挂单、成交、保护也不能压成同一个成功状态。
- **有效路径**：先固定草稿方向，再让 1R、估算和唯一执行按钮共用该方向。发送前保存请求编号和方向、委托类型，以同步引用锁住重复点击；发出 POST 后由原编号查询继续跟踪，旧网络响应必须同时匹配账户代次与仍在等待的编号才可更新。已受理轮询缩短到 1 秒，未找到请求保持原 3 秒节奏与封存次数。
- **通用规则**：流程简化应减少重复输入和无关等待，不改变授权点、交易纪律或回执含义。自动计算与手动输入要有独立切换入口；再次点击计算应重新计算，不能偷偷退出模式。
- **牵连**：`mobile/src/App.tsx`、`entryFlow.ts`、`useAutoStop.ts`、`TradeProgress.tsx`；`tests/discipline_app/serve_entry_ui_fixture.py` 使用假交易所验证连续点击、8 秒回执、14 秒超时回执及原编号查询，没有真实交易写请求。
