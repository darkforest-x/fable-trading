# 新通知通道需要独立投递状态与启用边界

- **问题**：已有 TG 信号监控新增 Bark，历史事件、成功回执和不确定发送仍需保持原义。一个信号可以在不同通道处于不同状态。
- **死胡同**：复用 TG outbox 或在启用 Bark 时给已有事件补队列，会把旧通知重放；单一 notification_status 也无法表达 TG 成功而 Bark 未启用、失败或结果未知。
- **有效路径**：共享不可变 event_id，按通道建立独立 outbox 和首次启用时间。队列只随首次事件插入在同一事务生成；发送端复核可见标记、启用后收盘和统一新鲜度。独立发送线程避免一个通道网络阻塞另一个通道。合成故障和并发测试覆盖原子回滚、一次领取与未知结果不盲目重试。
- **通用规则**：新增通知通道时先确定历史回放语义，再分离投递状态。服务接受、设备送达、用户已读是不同证据，不能因 HTTP 成功就冒充后两者。
- **牵连**：yoyo/monitor 的 Bark 私有配置、Store 双队列、service 双发送器及前端分通道状态。Bark 使用官方 POST /push，密钥仅在请求体及本机600权限配置；无密钥进入源文件、前端、队列或错误。没有新增定时 AI 巡检、改信号算法或修改其他项目通知配置。
