# 孤儿 stdio 工具进程可以拖停仍在监听的本机服务

- **问题**：2026-09-09 18:18，Spike 的 LaunchAgent 仍为 running，8766 TCP 可连接，但首页、health、status 均在 3–5 秒内返回零字节并超时。旧进程采样显示 Python GC 遍历期间其他线程等待 GIL；SQLite busy 是同时观察到的等待，不能据此认定数据库死锁。
- **死胡同**：18:20 仅重启 Spike 后，新的 PID 34247 仍频繁超时。正常模型推理锁、SQLite 只读查询及 TV 桥接超时均不足以解释这个现象。只看服务进程或重复重启会漏掉整机资源争用，还会重复全市场预热。
- **有效路径**：整机检查发现 25 个 PPID=1 的遗留 `ccxt-mcp/js/server.js` 进程合计占用约 832% CPU；全部 stdio 管道无对端、无网络 socket。样本在反复抛异常及写日志，源码的错误处理再次写已断开的 stderr，与异常循环吻合。精确核对 PID、父进程、完整命令、管道及 socket 后先发 TERM；退出失败后再次核对并结束这 25 个失联实例。保留有客户端的 MCP、虚拟机、浏览器及交易配置。未再次重启 Spike，首页/JS/health/status/signals 随即恢复 HTTP 200，实测 65–317ms，CPU 空闲回升至约 67%，扫描从停滞恢复推进。
- **通用规则**：`running`、TCP 监听、HTTP 响应、市场数据就绪是不同状态。先保留采样，再同时检查整机 CPU、内存、swap 与进程归属；清理必须限定已证明失联的实例，禁止泛杀 node。GC 停顿是阻塞位置，资源压力是本次有恢复对照支持的因素，不应进一步宣称已证实内存泄漏或 GC 损坏。服务恢复后仍需单独检查预热进度及扫描错误，HTTP 200 不等于全市场已就绪。
- **牵连**：本次仅恢复 `com.fable.impulse-monitor` 并清理失联工具进程，没有改 Spike 源码、指标、通知规则或外部工具安装文件。证据位于 `output/qa/spike_service_hang_20260909/`（两次进程 sample、清理前 PID 清单、逐 PID 清理回执、恢复接口探针）。此轮未修复 ccxt-mcp 上游退出处理，不能声称永久避免复发；如复发，针对 stdio 断管退出增加单独复现和修复。
