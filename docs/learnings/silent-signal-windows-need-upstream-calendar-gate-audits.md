# 信号空窗先查上游准入日历，再判断是否没有机会

- **问题**：2026-10-19 早晨，信号中心最新 V13.1 确认仍停在 10-18 06:00，用户询问为何一夜没有新信号。
- **死胡同**：只看确认事件数为零和扫描进程存活，只能证明页面与事件表一致，不能证明市场没有结构候选。单个 `v130:last_observation` 又只是最后一个合约周期的整个回放窗口，不能当成全市场昨夜统计。
- **有效路径**：用只读 SQLite 对照事件表、各合约的闭合 K 线覆盖和逐 bar `v9_reason`。北京时间 10-18 20:00（含）至 10-19 08:00（不含），489 合约 × 4 周期均覆盖窗口；536 个原始结构触发中，179 个在 V9 日历门仅报 `scheduled_open_utc_sunday`，另 7 个同时报量能问题，其余 350 个在更早结构/过热条件被拒。此处候选不是最终确认信号，也未声称取消日历门会新增同样数量的交易。V13.1 复用 V12.8 候选，后者继承 V9 的 UTC 周日排除；对应北京时间周日 08:00 至周一 08:00。当天 08:00 后已记录 GEV 15m 多头前级候选，回踩状态为等待。四个边界时间调用原 `entry_decision`，得到允许/拒绝/拒绝/允许，与代码和实际证据一致。
- **通用规则**：无信号诊断应分开验证行情覆盖、原始结构触发、逐级准入、回踩确认、事件写入与页面过滤；明确时间区间和时区。日历规则可能阻断新候选，却不代表此前候选不能继续确认，也不代表执行器停机。没有 owner 新授权，不删除既有交易过滤条件。
- **牵连**：`yoyo/evaluation/spike_v9.py` 的 `entry_decision`；`yoyo/monitor/v9_signals.py` → `v128_signals.py` → `v130_signals.py`/`v130_worker.py`；`yoyo/evaluation/pine/spike_burst_v13_1.pine` 的同一 UTC 周日条件；`HANDOFF.md` 的 2026-09-15 V9 过滤来源。此次仅诊断，未修改策略、实盘开关或事件表。
