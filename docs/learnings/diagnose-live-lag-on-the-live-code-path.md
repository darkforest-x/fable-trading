# 诊断实盘延迟要走实盘那条代码路径,离线统计会给出反向结论

- **问题**:前向日志 lag 中位 542 分钟 / 门 30 分钟 → 100% 拒单。
  我先后给出**两个错误病因**,都被后续测量推翻:
  1. "管道太慢" → 实测全宇宙 344 币扫描 **2.8 分钟**,算力从来不是瓶颈;
  2. "v11 检测器把框画在 200 根窗口中部(中位 33 根)" → 这个统计取自
     `mode="full"` 的离线扫描,而 live 走的是 `mode="live"`,**tip-edge 门
     本来就把框卡在盘口**。把 v11 放进 live 路径重测:框距盘口 p50=**1 根**,
     和 v9 一模一样。
- **死胡同**:用离线/全历史统计去解释实盘现象。同一份权重在 `mode="full"` 与
  `mode="live"` 下的框位分布差 33 倍,因为门控只在 live 生效。
  拿离线数字推实盘,等于在测一条根本没跑过的代码。
- **有效路径**:分离**墙钟时间**与 **K 线时间**。`detected_at − signal_time`
  混了两件事:框有多旧(K线时间)+ 多久才轮到这个币被扫(墙钟)。
  逐行看 `detected_at` 才看出真相——间隔是 **45 分钟一档**、且同一时刻批量
  出现多个币,即**每轮只扫一部分宇宙**,一个币隔几小时才被看一次。
  日志尾部(07-21)延迟已自行降到 17~78 分钟,说明那是**一段陈旧时期的统计**,
  不是当前管道的属性。
- **通用规则**:任何"实盘表现"归因,必须在实盘那条 code path 上复现
  (同 mode、同门控、同调度),并且把观测量拆成它混合的各个时间基准。
  一个跨越数天的中位数,先看它在时间上是否稳定——尾部自愈的指标说明
  病因已消失,继续修它是在修历史。
