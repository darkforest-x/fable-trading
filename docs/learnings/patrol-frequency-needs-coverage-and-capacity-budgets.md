# Patrol frequency must budget endpoint coverage, queue time and storage

- **Problem**: The owner proposed full-universe 5m/15m scans every 15 minutes, 1H every four hours and daily every two days. A shorter timer alone does not establish coverage or capacity.
- **Dead end**: Equating the first cached two-minute scan with sustainable throughput ignores later network-backed scans and machine contention. Treating the configured interval as actual cadence ignores the single worker. The latest-mode three-endpoint scan also leaves one endpoint unchecked when a 1H job runs every four hours.
- **Effective path**: Read the existing schedule, saved result metadata and worker code before changing configuration. On 2026-10-16, recent 285–286-coin 15m jobs took 352.697, 368.872 and 530.841 seconds from creation to completion; these are end-to-end durations, not isolated inference measurements. MPS was already used. Each result set contained about 16.9 MiB of JSON; 198.5 runs/day projects to roughly 3.275 GiB/day before database overhead. No full-market 5m timing was available, so equal-cost extrapolation remains an estimate.
- **General rule**: Schedule per newly closed endpoint, preserve the input/MA contract, and measure cold and warm full-universe cycles. Separate bootstrap from steady state, align clocks, let lower-frequency work yield to short-period work, and make delayed/backfilled results explicit. Accept a cadence only after measuring combined cycle completion with reserve. These are recommendations here, not implemented scheduler changes.
- **Affected**: `yoyo/yolo_workbench/worker.py`, `inference.py`, `market.py`, `store.py`. The current daily input requires 1,000 warmup plus 240 display bars (1,240 days), so “all symbols attempted” cannot imply every coin has a valid daily result. Do not silently reduce warmup or promote cross-timeframe model validity. Raw local evidence: `output/yolo-patrol-capacity-20261016/existing_job_evidence.json`. Existing hourly plan was left unchanged during this assessment.
