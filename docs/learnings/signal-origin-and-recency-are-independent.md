# 信号来源与新鲜度必须分开记录

- **问题**：12H 云带信号中心将历史补录和监控期间捕获的信号放在同一个“已确认”列表中。确认只说明形态规则成立，不能告诉使用者这条记录是否由在线监控及时发现。
- **死胡同**：只按确认时间排序、用页面加载时间判断“最新”，或只在卡片底部写“历史确认”，都不能解释数据来源。补录可能刚写入数据库；曾经实时捕获的信号也会自然变旧。
- **有效路径**：保留入库时不可变的 historical 来源字段，单独派生来源（实时捕获、启动前历史补录、启动后延迟补录）和随服务器时钟变化的新鲜度。默认实时入口只展示及时捕获且确认后不足12小时的记录，前30分钟标“新确认”；其余进历史，但不改写原始来源。历史入口、卡片和图表共同展示来源，通知仍由既有去重与时效规则决定。
- **通用规则**：先定义事件发生、首次捕获、启用和当前时间各自的含义。来源、显示窗口、通知时效及当前是否仍可交易是不同状态，不能共用一个“实时”布尔值；时间窗口不代表入场有效性。
- **牵连**：`yoyo/monitor/cloud_signals.py`、`yoyo/monitor/static/cloud-signals.js`；12H展示窗口/30分钟新确认；精确边界、未来时间、迟到记录、历史深链接和过滤后计数均需覆盖。原计划价格与通知状态不得因切换入口改写。
