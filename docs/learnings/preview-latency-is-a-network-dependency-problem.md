# 订单预览慢，要先拆网络依赖，再优化计算

- **问题**：手动实盘预览串行执行14次GET，其中余额重复3次；一次实测约49.4秒，主要耗在每次建连和等待交易所，而不是Decimal仓位计算。
- **死胡同**：把前端超时由45秒延到90秒只减少中断，不减少等待。仅在单次预览内建连接池仍有多条冷连接，首轮13.172秒；不能靠缓存旧余额、漏查算法单或放宽健康/报价门换速度。
- **有效路径**：将独立GET限制为4路并行，余额在本次预览内合并为同一份全账户回执，合约返回后提前请求档位，ticker仍最后新取。服务复用连接、不复用响应；每次请求重新签名且不携带cookie，失败不重试写入，预览副本不能进入真实执行器。最终真实只读3次为7.409、4.838、5.096秒，均12次GET；这是短时样本，不是网络延迟上界。
- **通用规则**：先记录各外部请求及依赖关系，再去重和并行；传输连接复用与业务数据缓存必须分开。对分页、失败关闭、账户身份、下一次预览重新读取、服务关闭释放连接分别验证。
- **牵连**：`yoyo/okx_execution/preview_reads.py`、`manual_api.py`、`client.py`、`tests/okx_execution/test_preview_reads.py`。只改变手动预览读路径；两个账户runtime、3%风险、3R/5R、闭合5m止损、5秒行情门、60秒确认期限及执行前重检保持。HTTPX连接池说明：https://www.python-httpx.org/advanced/clients/ 。原始耗时见`output/manual-ui-20261017/preview-latency-pooled.json`。
