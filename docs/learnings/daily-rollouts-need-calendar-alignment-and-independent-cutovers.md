# 新增日线监控必须同时固定日历边界和首次通知时间

- **问题**：Owner 于 2026-09-09 要求日线也发信号。日线可复用已有 `1Dutc` 数据，但按 Pine 自动高周期应新增 `1Wutc` 背景，且启用时不能补推昨天的日线箭头。
- **死胡同**：仅在周期列表增加日线会遗漏 API 字段长度、前端筛选、Bark 显示与 TV `interval=1D`。更隐蔽的是按 Unix epoch 整除一周会落到周四；真实 OKX UTC 周线从周一开始，解析器与高周期可用性判断必须一起修正，不能只修其中一处。
- **有效路径**：保留 `1Dutc` 标识及旧四周期数学规则，周线单独采用四天 epoch 偏移，解析、缓存截止判断、信号输入校验和 `_higher_at` 均按周一边界处理。通过真实公开 API 核对 UTC 周一，用合成时序验证日线开盘时只看已收周线，以及未来周线变更不影响既有结果。日线原始启动和 YOLO 确认沿用各自首次 cutover，测试旧周期元数据保持、昨日信号拒发、重启不移动 cutover、两条腿独立去重，30 分钟新鲜度不随日线拉长。
- **通用规则**：新增周期要检查日历锚点、因果可见时间、首次通知时间及显示标识四个契约。日线至少 341 根已收盘历史、周背景至少 341 周是原预热规则的自然结果，不能为新增周期暗改阈值；周背景未知不应被误当成可见启动的过滤条件。
- **牵连**：`yoyo/monitor/__init__.py`、`okx.py`、`signals.py`、`server.py`、`bark.py`、前端及 `tests/monitor/test_daily_enablement.py`。新增周数据流计入本机冷启动预算，VPS 脉冲、执行器、模型权重与 Pine 不变。此为工程支持，未验证日线模型质量或策略收益。公开契约来源：https://www.okx.com/docs-v5/en/#order-book-trading-market-data-get-candlesticks 。
