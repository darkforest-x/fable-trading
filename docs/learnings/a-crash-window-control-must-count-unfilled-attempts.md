# A crash-window control must count unfilled attempts

- **Problem**: After a 25-coin spike alarm, entering every same-side Monday 1.618 touch for 30 minutes made +80bp per trade. The open question was whether the 1.618 matters, or whether any dip bought in the same window would do as well. The control placed the signal's own limit geometry on the same coin at every other 5m bar of the same window (`exp-monday-limit-alarm-random-control-20261031-v1`).
- **Dead end**: The first summary compared each signal only with the controls of that event that filled, and found +17bp. That repeats the mistake in [limit-fill-complete-pairs-select-on-outcome.md](limit-fill-complete-pairs-select-on-outcome.md). A control limit fills only if price keeps falling after its bar, so the events where controls filled are the continuing crashes, where the signal also does badly. The 435 events with no filled control averaged +213bp and were dropped from that comparison.
- **Effective path**: Count every submitted control order, with an unfilled order as 0bp, and cluster by alarm episode. Per event the result is +80bp (signal +79.6 against control -0.8), with an episode bootstrap CI of +110 to +211bp, positive in every period. Then split the controls by offset from the signal's bar. Orders placed before the coin reached its 1.618 lose 50–161bp, and orders placed after the touch gain. The level acts as a "deep enough" marker inside the crash. A stricter volatility-bucket match narrows the gap to +37bp, and in 2020–24 it is about 0.
- **General rule**: When the control is a resting order inside a fast regime, never pair on control fills. Report attempt-level differences clustered by episode, show the mean of the excluded signals, and break the controls down by their timing relative to the signal.
