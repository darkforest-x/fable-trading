# 信号"慢"通常慢在证据寿命上，不在确认规则上

- **问题**：Owner 2026-09-22 说"突破+spike 有延迟"。直觉嫌疑是突破确认要"连续两根收盘超过线+0.2ATR"，
  以及上级周期要等整点收盘。
- **死胡同**：按这两条去估算，只能省 1–2 根 15m K，根本解释不了图上看到的"标出来时行情早就走了"。
  把确认根数从 2 改成 1 是个会改变信号定义的改动，却换不到多少及时性。
- **有效路径**：拿已有的全量账本把滞后逐段拆开（`analysis/p1_spike_v127_held_age_20260923.md`）：
  线出生 2 根，突破确认中位 1 根（75% 分位 2 根），上级可见中位 4 根——而**"先突破、后等 V9"中位 34 根、
  75% 分位 92 根、90% 分位 242 根**，且这类占联合候选的 72%。
  病因是状态机里的一个寿命常量：突破证据只要价格还站在冻结线上方，最长可以等 600 根再配对。
  把寿命压到 8 根后，整体滞后中位 13 根 → 2 根，入场追高中位 0.564R → 0.229R。
- **通用规则**：抱怨"信号慢"时，先把"事件被确认所需的根数"和"确认后还能等多久才被消费"分开量化。
  前者是确认规则，通常只有几根；后者是证据/状态的寿命，可以是几百根。**先量后改**：
  在账本里按环节报出中位与分位，再决定动哪个常量。同一个道理适用于任何"A 发生后等 B 出现才算数"的配对。
- **牵连**：`yoyo/evaluation/spike_v126_engine.py` 的 `pair_events(life=...)`、Pine 的 `v12Held`/`v12HeldHtf`
  与 `v10Life`；[held-break-is-state-not-a-time-window.md](held-break-is-state-not-a-time-window.md)
  解释了为什么它是状态而不是时间窗，本条补的是"状态也必须有被量化过的寿命"。
