# 分页接口的成功状态不能证明数据完整

- **问题**：A 股历史证券审计获取 BaoStock 全部基本资料时，已取两页共6000条，第三页发生墙钟超时；客户端却继续返回 `error_code=0`，使部分元数据看上去像一份完整快照。
- **死胡同**：只检查请求开始、每行及循环结束后的 `error_code`。SDK 的 `next()` 在网络返回空响应时直接 `False`，不更新错误码；其网络层还捕获所有 `Exception`，把我们原本的超时异常吞掉。因此首批成功状态会残留，接收行数与成功标志都不能证明末页完整。
- **有效路径**：墙钟中断使用仅在外层转换为业务错误的内部 `BaseException` 子类，绕过 SDK 的吞异常逻辑，防止部分数据写缓存。同时验证正常结束页：若停止时当前页仍等于分页容量，则无法证明已完成，必须拒收；正好整页的数据仍应请求下一空页确认结束。用合成完整页失败及 SDK 吞异常场景固定回归测试。失败缓存隔离保留，不拿缺失元数据作完整证券池依据。
- **通用规则**：分页数据的完整性需要终止证据，不能仅靠首个成功码。针对会吞异常的外部客户端，先证明取消和超时能穿透到缓存写入之前，再把其返回对象当可信快照。
- **牵连**：`yoyo/evaluation/ashare_data.py` 的 `result_frame()`、`query_timeout()`；`tests/test_ashare_data.py`。与网络连通性的区别见 `source-client-login-needs-response-and-wall-timeout.md`。
