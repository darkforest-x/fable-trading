# 交易自律限制需要服务端统一执行，复制界面不等于锁住账户

- **问题**：2026-10-18，Owner 要求新增独立的 iPhone / Android 合约交易 App，保留熟悉的 OKX 操作方式并加入纪律限制；明确不改现有模块。现有手动执行代码按止损计算数量，但没有账户级的开单次数、连续亏损或每日停手政策，且不接管交易所外部开仓。
- **死胡同**：本轮没有实盘试错。仅禁用手机按钮、降低界面显示的杠杆或按保证金百分比限制滑杆，都不足以形成执行边界：旧客户端、直接请求、未成交挂单、规则修改及 OKX 原生入口仍可能增加风险。多个客户端分别累计次数也会产生并发绕过。
- **有效路径**：本轮确定的设计方向是独立 App、独立服务与账本、明确账户归属。服务端在发送增加风险的指令前统一校验并预留预算；挂单、部分成交、撤改单与未知结果都要参与对账。冷静状态和政策版本持久化，限制放宽不能即时解除已触发的锁定。现有模块保持原样。此处是架构决策，尚未实现或验证实盘效果；示例参数不等于 Owner 批准。
- **通用规则**：先明确控制范围和可绕过渠道，再设计交易界面。App 退出后，已确认的交易所保护单应继续有效；持续自动管理依赖独立在线服务。系统只能约束经过其执行入口的订单，不能声称锁住 Owner 仍有权限直接交易的 OKX 账户。预算和止损均不能保证实际损失上限。
- **牵连**：核对依据为 `yoyo/okx_execution/manual.py`、`risk.py`、`manual_inventory.py` 与 `manual_commands.py`；这些文件本轮未修改。OKX 原生冷静期是另一种交易所限制，官方说明其覆盖多个渠道且对部分策略退出也有限制，不能未经账户和订单核对就代替自建入口风控：[官方说明](https://www.okx.com/zh-hans/help/trading-settings-faq)。移动端签名分发与浏览器原型须分别验收。
