# 统计缓存的版本必须跟账本变化走，而不是跟行情报价走

- **问题**：模拟盘每次读统计都扫描全部成交、仓位和分钟权益；换月份也重算全历史。
- **死胡同**：整个 SQLite 的 data_version 会被频繁报价与笔记写入失效，不能作为这类统计缓存的有效键。只缓存最后输出点数，也没有减少历史读取成本。
- **有效路径**：由 SQLite 触发器分别版本化账户账本和权益，所有写进程的已提交修改都可见。账本变化才重算精确 Decimal 统计；权益只读新增 bucket，合并可组合的首尾、极值与缺失点，最多 1200 点。修改、删除和倒序补录强制重建。版本与投影数据在同一读事务取得。
- **通用规则**：缓存失效要覆盖真实写者和修订语义，按用途分开版本；先证明金额口径不变，再比较暖读和首次构建。压缩图线不参与最大余额回撤等精确指标。
- **牵连**：`paper_history_cache.py`、`paper_desk_analytics.py`、`paper_desk.py`。真实副本 64 笔成交、25 仓位、5850 权益样本统计一致；暖读约 0.55–0.61 ms。额外 5 万样本暖读约 0.81 ms，但一次补入构建 166 ms 高于原全读 62 ms，不能把暖读速度宣称为冷启动提升。
