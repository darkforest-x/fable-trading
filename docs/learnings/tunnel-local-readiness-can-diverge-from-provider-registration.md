# Local tunnel readiness can disagree with provider registration

- **Problem**: On 2026-10-19 at 21:36 Beijing time, `https://spikeok.com/` returned HTTP 530 with Cloudflare error 1033. The application on 8766 and Caddy on 8780, probed with the required Host and HTTPS-forwarding headers, both returned 200.
- **Dead end**: The existing cloudflared process was running, its `/ready` endpoint returned 200 with `readyConnections=2`, and its metrics reported two connections. Those local assertions contradicted `cloudflared tunnel info`, which reported no active provider connection. Process liveness and even local readiness were insufficient evidence of public availability.
- **Effective path**: Reconnect only `com.spike.public-cloudflare` with `launchctl kickstart -k`, retaining the named tunnel UUID, hostname, credentials and ingress. Provider inspection then showed a newly registered connector. The public homepage, `/api/status` and `/static/app.js` returned 200; a real browser loaded the BTC chart and 494 market symbols. Other project service PIDs were unchanged by the reconnect. The exact cause of the earlier registration divergence was not established.
- **General rule**: Compare four independent observations: local application, correctly addressed local gateway, provider registration, and actual public HTTPS responses. When local readiness conflicts with the provider and public endpoint, treat the endpoint as unavailable and recover the connector before changing the application or DNS. Verify rendered data after HTTP recovery.
- **Related**: `yoyo/monitor/public_tunnel.py`, `yoyo/monitor/named_tunnel.py`, and the private `Fable/PublicTunnel/` runtime. The website forwards to 8766; stopping the unrelated 8642, 8765, 18766 and 5198 services does not remove that upstream. See [the earlier process-liveness lesson](tunnel-process-status-is-not-public-reachability.md) and [Cloudflare error 1033](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-1xxx-errors/error-1033/).
