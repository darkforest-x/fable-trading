# Tunnel process readiness does not prove public reachability

- **Problem**: On 2026-10-26, `https://spikeok.com/` returned HTTP 530 / Cloudflare 1033 while the local monitor and correctly addressed Caddy gateway returned HTTP 200. The connector was still running, with established TCP sockets and `/ready` reporting four connections, but `cloudflared tunnel info` reported no active connection.
- **Dead end**: Trusting the connector PID, TCP state, or its local readiness response would have misclassified this outage as a frontend failure. A bare request to Caddy also returned 421 because its host guard requires the public hostname; that was expected behavior, not a broken gateway.
- **Effective path**: Compare the origin (`127.0.0.1:8766`), gateway (`127.0.0.1:8780`, with `Host: spikeok.com` and `X-Forwarded-Proto: https`), public URL, and Cloudflare-side tunnel status. Restart only the verified `com.spike.public-cloudflare` LaunchAgent. The existing configuration registered new connections, the public homepage and status API returned 200, and a real browser rendered the paper chart. The monitor PID was preserved; the paper worker stayed alive and all four enabled patrol plans retained a current heartbeat.
- **General rule**: Keep process liveness, local connector readiness, control-plane connection status, and end-to-end browser availability separate. Recovery is demonstrated by the public application loading, not by a successful restart command. The evidence identifies stale/disconnected tunnel state; it does not establish the underlying network trigger or prove that the issue cannot recur.
- **Connections**: `yoyo/monitor/public_tunnel.py`, `yoyo/monitor/named_tunnel.py`, the existing private LaunchAgent configuration, and [Cloudflare's error 1033 documentation](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-1xxx-errors/error-1033/). No frontend design, trading configuration, credentials, or gateway policy changes were needed.
