# 开单日志必须跟随仓位生命周期，不能用币种定位

- **问题**：持仓卡片与历史仓位都要打开同一笔交易的开单逻辑、行情分析、计划与复盘；同币种会加仓、部分平仓、重新开仓，也可能同时有多个方向与杠杆。
- **死胡同**：设计时排除按币种存笔记或直接修改成交备注。币种会把不同交易混在一起；改成交备注会混淆当时提交的信息与事后复盘。仅把草稿放进列表渲染状态还会被异步轮询重建，造成光标跳动或输入丢失。
- **有效路径**：日志单独以稳定的 position_id 持久化，读取不依赖行情、不创建空记录。合并加仓及部分平仓沿用该标识，全部平仓后仍可编辑，重新开仓生成新标识。保留原始 note，作为未建日志时的初始开仓逻辑。保存用版本比较阻止静默覆盖；同一版本、同一内容的网络重试返回已保存记录。弹窗编辑期间保留 DOM，并对迟到响应校验编辑实例；冲突时保留本地草稿并展示最新内容供选择。
- **通用规则**：为交易增加可编辑业务资料时，先明确它属于委托、成交还是完整仓位生命周期；资料独立保存、原始交易事实不改写，列表高频刷新不要携带长文本。
- **牵连**：`yoyo/research_workspace/paper_desk_journal.py`、`paper_desk.py` 的 position_journals 与账户导出版本 7、`paper_desk_api.py` 日志接口、`yoyo/monitor/static/paper-desk.js` 弹窗与卡片入口。临时 SQLite 和独立浏览器账户验证保存、重启读取、历史仓位、重新开仓隔离与并发冲突；不向用户账户写入验收交易或示例日志。
