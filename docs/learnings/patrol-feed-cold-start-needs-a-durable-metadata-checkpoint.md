# 巡检列表的热缓存成功不能证明重启后能及时显示

- **问题**：2026-10-31 巡检页一直读取，原浏览器保留了 15 秒请求超时错误；但随后接口读取约 0.15 秒。服务内存缓存掩盖了首次查询必须扫描约 84.7 万条结果、13 GB 账本的问题，独立冷读超过三分钟仍未完成。
- **死胡同**：只重复请求已经预热的接口会误判为恢复。将 SQLite 循环顺序改为先展开形态、再读取任务清单，虽然避免为空结果反复解析任务元数据，但首次重建仍需约 70 秒，不能独自满足首屏预算。单纯延长浏览器超时也不会消除每次重启的全历史扫描。
- **有效路径**：在账本旁原子保存精简原始形态观测和同一快照的 rowid 高水位；启动时恢复，再读取新增结果。必须保留原始观测，不能只缓存合并卡片，否则历史翻页 cutoff、首次发现与跨扫描合并会改变。按数据库设备/inode 和缓存协议版本隔离，源高水位回退或缓存损坏时重建，缓存写入失败仍可显示本次真实结果；至多每分钟落盘一次，不改观察账本或巡检进程。
- **证据**：27,138 条原始形态观测压缩为约 1.8 MB；首次构建 69.88 秒，独立恢复 0.93 秒，热读 0.10 秒。冻结同一 cutoff 后，9,813 处历史形态的全部字段与旧线上接口逐条一致；故障回归覆盖损坏/错版本缓存、数据库替换与回退、增量续读、分页和写入失败。SQLite [CROSS JOIN 的固定循环顺序](https://www.sqlite.org/optoverview.html#manual_control_of_query_plans_using_cross_join) 是局部查询优化，持久检查点才消除了正常重启的全量重扫。
- **通用规则**：页面超时而接口随后很快时，先保存原页面错误，再分别测首次读、恢复读和热读；性能验收必须包括重启。派生缓存可以丢弃，但不能改变来源、时间边界或分页语义。
- **牵连**：`yoyo/yolo_workbench/discoveries.py`、`tests/yolo_workbench/test_discoveries.py`；原始验证保存在 `output/playwright/patrol-loading-20261031/`，运行缓存为账本旁 `discoveries-v1.json.gz`。无界面设计、模型、交易设置或历史记录变更。
