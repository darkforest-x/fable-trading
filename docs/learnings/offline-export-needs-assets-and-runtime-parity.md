# A portable export must include runtime behavior and the full asset closure

- **Problem**: The owner requested a single HTML matching the RektProof frontend, including its chapter directory, originals, cases, and replay exercises. The existing booklet HTML contained prose but did not include the full frontend or independent image resources.
- **Dead end**: Sending that existing HTML would lose frontend interactions and leave image paths dependent on the source machine. Direct `file://` browser QA was also rejected by the browser URL policy; no alternate browser route was used to bypass it.
- **Effective path**: Reuse the current frontend JS/CSS, assert every narrowly scoped packaging substitution, embed JSON and byte-identical media, deduplicate assets by SHA-256, and resolve them to Blob URLs. Keep offline learning storage separate from the live app. Validate every media hash, execute all seven rendered views and 23 chapters without network access, and retain the distinction between runtime checks and browser visual QA.
- **General rule**: Before exporting an interactive page, enumerate its data, assets, runtime, and user-state dependencies. Include the first three, exclude the sender's personal state, and test the packaged bytes rather than assuming the live page proves the export.
- **Scope**: Private builder `~/Documents/Codex/2026-10-15/rektproof/work/offline.py`; current `rektproof.js`, `rektproof-study.js`, `rektproof-core.js` and styles; Telegram Bot API multipart document limit of 50 MB checked on 2026-10-15. The produced HTML was 43,824,703 bytes. This task did not change trading parameters or eligibility.
