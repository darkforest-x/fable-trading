# 内部淘汰必须自动补位，不能变成 Owner 审核任务

- **问题**：Owner 要的是一批达到固定标准的有框样例，管道却把候选池的内部拒绝结果也作为“无框图”交付，并要求 Owner 再做 KEEP / ADJUST / REJECT；这把检索器没有完成的工作转嫁给了 Owner。
- **死胡同**：冻结原来 50 个身份后只在这 50 个中做严格裁决，虽然“宁缺毋滥”，但会自然得到有框/无框混合包。这个方法适合标签审计，不适合“从大候选池交付 N 个合格样例”；再精细的无框理由也修复不了任务类型错位。
- **有效路径**：先区分“审核固定身份”和“检索固定数量”两种合同。后者必须把拒绝保留在内部，从冻结大池继续补位，直到交付数量、每图框数和质量门同时满足；发送器还要 fail-closed 验证 50/50 有框，并在文案中明确没有人工裁决动作。
- **通用规则**：用户要求“找 N 个/发 N 张合格样例”时，第一步冻结的是数量与质量合同，不是首批 N 个候选身份。除非用户明确要求看淘汰原因，否则无框、REJECT 和不确定样本只进内部审计账本，不进入交付包。
- **牵连**：`yoyo/datasets/ma_launch_owner_autofill_review.py`、`scripts/send_15m_ma_launch_owner_autofill50.py`、`exp-15m-ma-launch-owner-strict-review50-v5`（错误任务类型）、`exp-15m-ma-launch-owner-autofill50-v7`（自动补位合同）；仍受 holdout=0、无 labels、无训练、无 production 的安全门约束。
