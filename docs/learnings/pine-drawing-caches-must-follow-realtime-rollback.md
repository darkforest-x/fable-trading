# Pine drawing caches must follow realtime rollback

- **问题**：V2.7 deleted and recreated every visible trade box, label and polyline on each last-bar execution. The entry caption “空 0R” also confused the entry origin with the trade outcome.
- **死胡同**：A `varip` timestamp gate was considered and rejected before implementation: drawings created on an earlier realtime tick can roll back while a `varip` flag survives, leaving the chart blank. Cutting requested history was also rejected because the owner requires historical frames and previous shared-request truncation already caused missing trades. Profiler CPU estimates do not measure network or chart-render latency.
- **有效路径**：V2.8 uses ordinary `var` frame records with their drawing handles, exact serialized-row/finish comparisons, and delete-before-create reconciliation only for changed frames. Closed frames reuse committed IDs; live frames extend when their confirmed finish changes. The last confirmed history bar seeds drawings when its source snapshot exists. Initial uncommitted realtime drawings may still need recreation until chart-bar commit. nPOC serialization is refreshed only on list mutation; all numeric key-level calculations and the complete trade engine remain unchanged. Native 15m checks compare the old/new key engine over 10,679 bars, preserve the 146-trade ledger signature, and assert zero extra allocations on a second unchanged-frame reconciliation.
- **通用规则**：Inspect source/history costs separately from display costs, pair cache lifetime with Pine rollback, and preserve source chronology. Viewport changes restart scripts that use visible-bar timestamps; a rendering cache cannot eliminate this full recalculation. Do not promise a percentage speedup from a single profile sample.
