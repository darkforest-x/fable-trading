# A desktop chart opener must be verified from its actual service context

- **Problem**: spike needed one-click Mac TradingView navigation with the selected contract and timeframe. A registered URL scheme and a successful AppleScript return were both insufficient evidence of actual chart navigation.
- **Dead ends**: TradingView 3.4.0's registered scheme handled login, not chart links. Clicking the native macOS clipboard menu returned without changing the chart. A direct Codex-shell script then succeeded through the window's internal clipboard menu, but the same script failed from the caffeinate-wrapped LaunchAgent with AppleEvent timeout -1712. The live system's Automation panel showed `caffeinate → System Events` disabled.
- **Effective path**: use the documented clipboard workflow through the desktop window menu, select its current accessibility element rather than fixed screen coordinates, and verify both symbol and interval in the actual chart. Keep an independent same-origin POST button and in-page preview. Check permissions in the service's actual process context. Direct tests opened BTC 4H and TRUTH 15m in the saved 综合过滤 layout; live service acceptance remains pending the owner's one-time system permission switch.
- **General rule**: separate four observations: URL registration, command dispatch, actual UI navigation, and deployment-context permissions. A pass at an earlier boundary does not prove the next. Clipboard cleanup needs an operation deadline inside the outer process timeout; per-event AppleScript timeouts alone do not bound a recursive traversal. Preserve a user's intervening clipboard copy and reject it before dispatch rather than opening different clipboard data.
- **Affected paths**: `yoyo/monitor/tradingview.py`, `tradingview.applescript`, `server.py`, static watch/detail controls, and `tests/monitor/test_tradingview.py`. No trading, notification or detector configuration changes. Owner explicitly authorized AppleScript on 2026-09-08; no OS permission was changed by the implementation.
