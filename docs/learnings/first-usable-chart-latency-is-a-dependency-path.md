# 首个可用图表的延迟取决于依赖路径，不只取决于单个接口耗时

- **问题**：公网单次接口约 1–2 秒，但浏览器冷缓存打开 1.618 页面时，代码和数据依赖直到约 12.9 秒才齐备；未缓存周期切换经过两次请求，约 4.4 秒。
- **死胡同**：只让静态文件命中 CDN 仍会被大量请求排队和依赖串行阻塞。首次试验确认 HIT，却仍有约 10 秒的资源就绪时间。立即返回空的 `loading` 快照也不等于快：客户端轮询间隔和第二次公网往返都在首屏关键路径上。
- **有效路径**：保留 JS 执行顺序和 CSS 懒加载插入位置，把全站 14 个启动脚本、15 个主样式合为 1+3 个内容版本资源；提前并行获取路由代码与只读快照。K 线冷请求有界等待首个经过校验的 240 根已收盘数据，余下历史继续由原有两个后台任务补齐。失败保留首屏数据并明确重试未补齐历史，不能因首屏已新鲜而永久漏掉历史。
- **通用规则**：先记录请求依赖、排队和首个可用响应，再决定缓存或并行化。用真实浏览器检查版本命中、快速切换身份、取消请求、历史补齐视野和其他页面；不要把 CDN HIT、接口 TTFB 或本机热缓存直接称作首屏完成。本次公网单次对照的依赖就绪约 12.9→8.6 秒，周期响应约 4.4→1.7 秒；不是稳定延迟保证或真实绘制帧时间。
- **牵连**：`asset_delivery.py`、`startup-hints.js`、`monday_candles.py`、共享图表工具。只缓存有匹配内容版本的公开代码；HTML、行情与账户 API 继续 `no-store`。等待者最多 8 个、等待上限 8 秒，取数仍用原后台限速与 2 个任务槽，不能抢监控优先级。CSS 遇到不支持的 import/相对 URL 保留原链接。原始对照保存在 `output/public-perf-20261023/`；缓存语义参考 [Cloudflare 官方规则](https://developers.cloudflare.com/cache/concepts/default-cache-behavior/)。
